Review the following design notes for a CPU inference engine. Explain the main tradeoffs, propose a measurement plan, and identify which correctness properties must remain unchanged when the implementation is optimized.

The engine reads a large mixture-of-experts checkpoint from several tensor files. Every decoder layer has a small router, many independent experts, a shared feed-forward branch, and either recurrent attention or a key-value attention cache. Each token selects only a few experts. Total model size determines storage and capacity requirements, while the active subset determines much of the arithmetic and memory traffic per token. These quantities should be reported separately.

The memory planner reserves causal state and temporary arrays before deciding how many weights can remain resident. Frequently reused attention matrices and the output projection receive priority. Remaining capacity is distributed among per-layer expert caches. New experts are loaded lazily. A cache miss must not discard a usable entry if the incoming tensor is corrupt or truncated, and the order of accesses must reproduce the intended least-recently-used policy. Compare this approach with loading every weight before the first request.

Prompt processing can combine many token projections into matrix operations, but generation usually advances one token at a time. A larger prompt block may reuse an expert's weights across multiple token inputs. It also requires more temporary outputs and changes how much work is discarded after an error. Attention still has to respect causal ordering. A recurrent state update must not observe a future token, and a key-value query must see exactly the valid prefix for its position.

Parallel scheduling has several costs beyond arithmetic. Workers may wait for storage, contend over allocator locks, compete for memory bandwidth, or spend time launching tiny tasks. The processor may have cores with different capabilities. Nested parallel operations should reuse a bounded worker pool rather than creating additional threads. Explain why maximizing thread count does not necessarily minimize latency, and how to separate scheduling overhead from time spent in the matrix kernels.

Numerical behavior also matters. The stored weights use a compact floating-point format, intermediate products accumulate at higher precision, and selected boundaries round back to the activation format. Optimizations should preserve the defined reduction order where exact replay is required. Tests should include signed zero, values close to rounding ties, finite overflow, non-finite inputs, unaligned tails, and failures late in a projection. A faster path must still report the first relevant error and leave reusable state in a defined condition.

Finally, design a benchmark that distinguishes loading, prompt processing, and generation. Record both fresh runtime caches and repeated requests with resident weights. Reverse the order of candidate and control runs, use several input lengths and subjects, compare generated token IDs and complete output scores, and track expert misses alongside peak memory. Discuss which conclusions can be drawn from a kernel microbenchmark and which require an end-to-end measurement. Recommend a small set of concrete next experiments based on these notes.
